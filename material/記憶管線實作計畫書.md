## 1. 文件目的

Furet 現在已有：

- `memory_save` 寫入每日記憶。
- `memory_search` 搜尋日常記憶。
- `memory_add`／`memory_replace`／`memory_remove` 維護 `MEMORY.md`。
- session archive、FTS、embedding 與每日 journal。
- PEOPLE、OWNER、MEMORY、daily memory 的責任分層。

缺少的是一條可靠的背景管線，把「對話中值得記住的候選事項」與「長期記憶的整理、去重、升級、淘汰」分開處理。

本計畫建立兩階段流程：

```text
Session / events
  → Extraction：抽取結構化記憶候選，不直接改長期記憶
  → Candidate store：可重試、可去重、可追溯
  → Consolidation：比對現有 MEMORY/PEOPLE/daily，產生明確 mutation plan
  → Apply：在 lock/lease 下原子寫入
  → Reindex / audit
```

核心原則：

> LLM 負責提出候選與語意判斷；程式負責權限、去重、鎖、版本、套用與稽核。不能讓一次自由生成直接覆寫整份記憶。

## 2. 目標與非目標

### 2.1 目標

1. 將 extraction 與 consolidation 分離。
2. 候選資料結構化，保留來源、時間、對象、信心與敏感度。
3. 支援 idempotency、retry、lock/lease 與 crash recovery。
4. 遵守 OWNER／PEOPLE／MEMORY／daily memory 的既有責任邊界。
5. 避免重複、矛盾與將短期事件錯升級成長期事實。
6. 所有 mutation 以小範圍 diff/operation 套用，不整檔自由重寫。
7. 對私人與敏感內容採最小保存、最小揭露。
8. 保持目前搜尋索引與 embedding 一致。
9. 讓人工或主 Agent 能檢視「為什麼記住、從哪裡來、做了什麼修改」。

### 2.2 非目標

第一版不做：

- 把每句聊天都永久保存。
- 自動修改 OWNER.md。
- 讓 Subagent 直接呼叫 `memory_add/replace/remove`。
- 以單次 LLM 回覆覆蓋整份 `MEMORY.md` 或 `PEOPLE.md`。
- 把完整 session、附件或私人文件複製進長期記憶。
- 無限期保存所有候選與 audit payload。
- 對高度敏感資訊做向量索引或在 log 中留下原文。
- 取代每日 journal；journal 是敘事紀錄，memory pipeline 是可操作事實與偏好管理。

## 3. 現有記憶責任邊界

必須延續目前規則：

### 3.1 `OWNER.md`

- 只描述唯一 owner 的身分、稱呼與權限。
- 不由背景管線自動修改。
- 若候選涉及 owner 身分規則變更，只能進入人工審核狀態。

### 3.2 `PEOPLE.md`

- 儲存其他人的身分、稱呼、互動特徵與權限。
- 新人物第一次出現可產生候選。
- Discord ID 是主要 identity key；暱稱不是穩定主鍵。
- mutation 必須使用 people repository／既有 `people_*` 同等的 typed 操作，不能整檔覆寫。

### 3.3 `MEMORY.md`

- 長期規則、偏好、持續超過約 30 天的重要事實、重要開發決策與 owner 世界中的穩定資訊。
- 短期事件不能只因最近被提到就自動升級。
- 更新既有資訊優先於新增重複條目。
- 容量接近上限時先 consolidation/prune，再新增。

### 3.4 `memory/YYYY-MM-DD.md`

- 記錄當天發生的事、社交聊天與短期決策。
- extraction 可優先寫 daily memory，但仍需去重。
- 不應把整段對話原文複製進去；保存摘要與必要來源指標。

### 3.5 Session archive

- 是對話證據來源，不是 long-term memory 本身。
- current session 未必已進 archive；管線需能接受 live session snapshot 或 event envelope。
- 讀取 session 要遵守權限與敏感資料邊界。

## 4. 整體架構

```text
Session close / periodic trigger / explicit memory hook
  ↓
Extraction job
  ├─ select eligible messages/events
  ├─ redact/limit payload
  ├─ LLM or deterministic extraction
  └─ write MemoryCandidate[]
  ↓
Candidate store (SQLite)
  ├─ dedupe key
  ├─ source reference
  ├─ state machine
  └─ retry metadata
  ↓
Consolidation job
  ├─ acquire lease
  ├─ load relevant current memory
  ├─ classify destination
  ├─ detect duplicate/conflict/staleness
  ├─ produce MemoryMutationPlan
  └─ validate plan
  ↓
Apply transaction
  ├─ typed repository operations
  ├─ atomic file write
  ├─ index/vector update
  ├─ audit record
  └─ mark candidates applied/rejected/deferred
```

## 5. Trigger 設計

### 5.1 Extraction 觸發時機

可支援：

- session archive 完成後。
- session 達到一定訊息數或 token 門檻。
- 每日 journal 前的增量抽取。
- 主 Agent 明確呼叫 memory hook。
- owner 明確要求「記住這件事」時立即建立高優先候選。

避免每則訊息即時呼叫模型，會造成成本、競態與大量低價值候選。

### 5.2 Consolidation 觸發時機

- 固定低頻 cron，例如每日一次。
- 候選數達門檻。
- `MEMORY.md` 接近容量限制。
- owner 主動要求整理記憶。

### 5.3 Trigger 不等於授權

背景 cron 可以處理已允許的記憶類型，但不能因此取得 owner-only 外部工具或任意檔案寫入權。

## 6. 記憶候選資料模型

```ts
type MemoryDestination =
  | "daily"
  | "long_term"
  | "people"
  | "owner_review"
  | "discard";

type CandidateState =
  | "pending"
  | "leased"
  | "applied"
  | "rejected"
  | "deferred"
  | "failed";

interface MemoryCandidate {
  id: string;
  dedupeKey: string;
  subjectKey: string;
  kind: "fact" | "preference" | "decision" | "event" | "relationship" | "instruction" | "correction";
  summary: string;
  destinationHint: MemoryDestination;
  occurredAt?: string;
  observedAt: string;
  source: {
    sessionId?: string;
    channelId?: string;
    messageIds?: string[];
    eventType: string;
  };
  confidence: number;
  sensitivity: "normal" | "private" | "high";
  durability: "ephemeral" | "short" | "long" | "unknown";
  explicitRememberRequest: boolean;
  contradictsCandidateId?: string;
  state: CandidateState;
  attempts: number;
  nextAttemptAt?: string;
  createdAt: string;
  updatedAt: string;
}
```

### 6.1 最小內容原則

candidate store 保存摘要與來源指標，不預設保存完整對話。需要重新驗證時，透過 message/session ID 讀取原始來源；來源不可用時，降低信心或轉人工審核。

### 6.2 Dedupe key

可由以下組合產生：

```text
normalized subject + kind + normalized semantic key + time bucket
```

不能只 hash 完整文字，因為同一事實可能有不同說法。

## 7. Extraction 階段

### 7.1 輸入選擇

只抽取具潛在價值的內容：

- 明確偏好或長期規則。
- 關係、稱呼、身份修正。
- 已完成的重要決策。
- 待辦與有時效的承諾。
- 開發架構與安全規範。
- 旅行、健康等 owner 主動提供且確實有後續用途的資訊。
- 對 bot 行為的重要糾正。

通常不抽取：

- 一次性玩笑。
- 無後續價值的寒暄。
- 模型推測。
- 未經證實的第三方八卦。
- 重複的 tool output。
- secret 原文。

### 7.2 Extraction 輸出約束

- 僅輸出 `MemoryCandidate[]` JSON。
- 不可呼叫 mutation tools。
- 每個 candidate 必須附 source IDs。
- 區分「使用者明說」與「模型推論」。推論不得直接成為高信心長期記憶。
- 遇到更正時建立 `correction`，指向可能過時的候選／記憶項。

### 7.3 可由 deterministic rule 處理的內容

不必全部交給 LLM：

- owner 說「記住：...」可直接建立 explicit candidate。
- Discord user ID 與 username 可從 event metadata 帶入。
- tool 已成功建立的 reminder/task/PR 可由 structured event 產生候選。
- tool 失敗不能被記成已完成。

### 7.4 Subagent 使用方式

若採用 [Subagent 計畫書](./Subagent實作計畫書.md)：

- worker 僅收到去識別、最小化的 message window。
- 使用 `memory-extraction` 工作模式，但不是固定人格職位。
- 不載入完整 MEMORY/PEOPLE，不可寫入。
- 回傳候選給主 pipeline。
- 私人／高敏感資料可選擇完全不交給 worker，由主流程處理。

## 8. Candidate Store 與狀態機

建議使用 SQLite，而不是把 queue 寫成散落 JSON。

### 8.1 表格方向

```sql
memory_candidates(
  id TEXT PRIMARY KEY,
  dedupe_key TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  state TEXT NOT NULL,
  lease_owner TEXT,
  lease_until TEXT,
  attempts INTEGER NOT NULL DEFAULT 0,
  next_attempt_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

memory_mutations(
  id TEXT PRIMARY KEY,
  candidate_ids_json TEXT NOT NULL,
  plan_json TEXT NOT NULL,
  status TEXT NOT NULL,
  before_hash TEXT,
  after_hash TEXT,
  created_at TEXT NOT NULL,
  applied_at TEXT
);
```

### 8.2 State transitions

```text
pending → leased → applied
                 → rejected
                 → deferred
                 → failed → pending（retry）
```

- lease 過期可由其他 worker 接手。
- applied mutation 需 idempotency key，重跑不能重複加入。
- failed 超過上限進 dead-letter/deferred，通知主 Agent或 owner。

## 9. Lock、Lease 與競態控制

### 9.1 為什麼需要

可能同時發生：

- Discord 對話中呼叫 `memory_save`。
- cron 正在 consolidation。
- journal job 讀取 daily memory。
- 另一個 session 更新 PEOPLE/MEMORY。

沒有 lock 會造成 lost update 或重複寫入。

### 9.2 建議策略

- SQLite transaction 取得 job lease。
- 每個目標檔案有 logical lock key。
- apply 前計算 `beforeHash`。
- 寫入前再次檢查 hash；若已改變，重新載入與重算 plan。
- 使用 temp file + fsync + rename 做 atomic replacement。
- lock 有 TTL，程序 crash 後可恢復。

### 9.3 不允許

- 長時間持有檔案 lock 等待 LLM。
- 先讀 MEMORY、呼叫模型數分鐘、然後無條件覆寫舊 snapshot。
- 使用 Bash 拼接修改核心記憶檔。

## 10. Consolidation 階段

### 10.1 輸入

- 一批相關 pending candidates。
- 現有目標記憶的最小相關片段。
- destination rules。
- 容量與敏感度政策。

### 10.2 任務

1. 群組同一 subject/topic。
2. 合併重複候選。
3. 偵測與現有記憶的重複或矛盾。
4. 判斷 daily、long-term、people、review、discard。
5. 對長期記憶判斷穩定性與未來用途。
6. 產生小範圍 mutation plan。
7. 為每個 candidate 指定 outcome 與理由。

### 10.3 Mutation plan

```ts
type MemoryMutation =
  | { op: "appendDaily"; date: string; content: string }
  | { op: "addLongTerm"; section: string; content: string }
  | { op: "replaceLongTerm"; oldText: string; newText: string }
  | { op: "removeLongTerm"; text: string }
  | { op: "addPerson"; personKey: string; content: string }
  | { op: "updatePerson"; oldText: string; newText: string }
  | { op: "deferForReview"; reason: string }
  | { op: "discard"; reason: string };

interface MemoryMutationPlan {
  id: string;
  candidateIds: string[];
  mutations: MemoryMutation[];
  rationale: string[];
  expectedBeforeHashes: Record<string, string>;
}
```

### 10.4 不直接輸出完整檔案

LLM 不應產生「新的整份 MEMORY.md」。應輸出 operation，程式檢查 substring 唯一性、section 邊界、容量、wrapper integrity 後才套用。

## 11. 目的地判斷規則

### 11.1 Daily memory

適合：

- 今天發生的事件。
- 短期待辦與進度。
- 社交互動。
- 一次性但值得寫入日誌的教訓。

### 11.2 Long-term MEMORY

適合：

- 穩定偏好與明確規則。
- 長期持續的專案架構決策。
- 未來多次會用到的 owner 世界資訊。
- 已反覆出現或明確要求長期記住的事項。

需保守處理：

- 健康資訊。
- 尚未確定的計畫。
- 情緒性暫時表述。
- 第三方私人資訊。

### 11.3 PEOPLE

適合：

- 新人物 identity。
- 稱呼與別名。
- 穩定互動風格。
- 已明確確認的關係與權限。

不得因單次玩笑直接寫成穩定人格描述。

### 11.4 Owner review

必須人工審核：

- OWNER.md 變更。
- 高敏感資訊。
- 來源矛盾且影響權限／稱呼。
- 刪除大量長期記憶。
- 無法確定是否為玩笑或事實。

## 12. 矛盾、修正與時間性

### 12.1 新資訊不一定覆蓋舊資訊

需區分：

- 更正：舊資訊本來就錯。
- 時間更新：舊資訊曾經正確，現在改變。
- 暫時例外：不應改掉一般規則。
- 多來源衝突：需要人工判斷。

### 12.2 時間欄位

對會變動的資訊保存有效時間，例如：

```text
自 2026-08-19 起，systemd service 使用 Restart=always
```

避免把歷史狀態改寫成無時間脈絡的絕對事實。

### 12.3 Source priority

建議優先度：

1. owner 明確更正。
2. 成功 tool result／系統事件。
3. owner 明確陳述。
4. 已知人物自行陳述。
5. 第三方轉述。
6. 模型推論。

低優先來源不能無條件覆蓋高優先記憶。

## 13. 敏感資料與隱私

### 13.1 分級

- `normal`：一般偏好、公開開發決策。
- `private`：私人行程、關係、健康摘要。
- `high`：credentials、recovery codes、token、完整醫療文件、私人文件內容。

### 13.2 高敏感資料

- 不進 candidate 原文。
- 不進 embedding。
- 不進一般 log。
- 若需記住，只保存「位置／處理狀態」等最小 metadata，敏感內容本身留在安全儲存。
- 不交給 Subagent。

### 13.3 刪除與更正

owner 要求忘記某事時：

- 對所有目的地建立 tombstone/removal mutation。
- 更新搜尋索引與向量。
- audit 只保留不含被刪內容的操作 metadata。
- 後續 extraction 不得因舊 session 再次復活已明確刪除的記憶；需有 suppression/tombstone key。

## 14. Repository 與寫入 API

將目前 tool 寫檔邏輯抽成可重用 repository，工具與背景管線共用同一套驗證：

```text
src/memory/
  types.ts
  candidate-store.ts
  extractor.ts
  consolidator.ts
  repository.ts
  locks.ts
  policy.ts
  index-sync.ts
  scheduler.ts
```

示意：

```ts
interface MemoryRepository {
  appendDaily(input: AppendDailyInput): Promise<WriteResult>;
  addLongTerm(input: AddLongTermInput): Promise<WriteResult>;
  replaceLongTerm(input: ReplaceLongTermInput): Promise<WriteResult>;
  addPerson(input: AddPersonInput): Promise<WriteResult>;
  updatePerson(input: UpdatePersonInput): Promise<WriteResult>;
  applyPlan(plan: MemoryMutationPlan): Promise<ApplyResult>;
}
```

工具層仍做 owner/identity 權限；repository 做資料完整性、lock、atomic write 與 index sync。

## 15. 索引一致性

每次成功 mutation 後：

1. 更新實體檔案。
2. 更新 FTS。
3. 更新或移除 embedding。
4. 記錄 file hash/index version。
5. 若 index update 失敗，標記 repair required，不能假裝全部成功。

建議建立 reconciliation job：掃描 file hash 與 index metadata，修復 drift。

### 15.1 Transaction 邊界

檔案系統與 SQLite 無法自然共享同一 transaction，因此需採 saga/outbox：

- 先寫 mutation intent。
- atomic 寫檔。
- 更新 DB/index。
- 標記完成。
- crash 後依 intent 與 hash 判斷續做或補償。

## 16. Retry、Dead Letter 與可觀測性

### 16.1 Retry

- 暫時性 API/network error：指數退避。
- parse/schema error：有限次重試後 deferred。
- source missing：降低信心或 review。
- hash conflict：重新 consolidation，不直接重試舊 plan。

### 16.2 Dead letter

候選超過最大嘗試次數後：

- 標記 `deferred`。
- 保存不含敏感原文的錯誤摘要。
- 透過秘書辦公室或日報報告需要注意的異常；一般無價值候選可靜默丟棄。

### 16.3 Metrics/log

- extraction jobs/count/duration
- candidates produced/deduped/rejected
- consolidation batch size
- mutations by destination/op
- conflicts/hash retries
- failed/deferred count
- index repair count

沿用完整 Error cause chain，保留底層錯誤 code；不得記錄 secret 或完整私人對話。

## 17. 與 Bash Policy 的整合

依 [Bash 指令政策計畫書](./Bash指令政策實作計畫書.md)：

- 背景記憶 job 不使用 unrestricted Bash。
- repository 使用 Node API 與 atomic write，不靠 shell 編輯文件。
- migration/repair script 只由 owner-interactive profile 執行。
- scheduled task profile 不允許任意 command interpolation。
- memory pipeline 的權限與資料驗證不能只依 Bash policy；兩者是不同防線。

---

## 18. 與 Subagent 的整合

依 [Subagent 計畫書](./Subagent實作計畫書.md)：

- Subagent 可以協助 extraction 或 conflict analysis。
- Subagent 不載入完整私人記憶，只取得任務必要片段。
- 不可呼叫 `memory_save`、`memory_add`、`memory_replace`、`people_*`。
- worker 結果視為不可信建議，需經 schema validation 與 pipeline policy。
- timeout 要真正 abort，遲到結果不得套用。
- 主 Agent／scheduler 對最終 mutation 負責。

## 20. Shadow Mode

正式自動寫入前先跑 shadow mode：

- extraction 正常產生 candidates。
- consolidation 產生 plan。
- 不套用檔案。
- 把 proposed diff、原因、candidate outcomes 存入 audit。
- 與人工／現有 memory hooks 的結果比較。

建議至少觀察數天，確認不會：

- 把玩笑當事實。
- 重複新增。
- 覆蓋正確舊資訊。
- 把短期事件升成長期記憶。
- 洩漏敏感內容。

## 21. 實作階段

### Phase 0：現況測繪

- 盤點 memory tools、session archive、journal、DB/FTS/vector。
- 定義 destination policy 與敏感度分類。
- 同步更新 `material/DESIGN.md`。

### Phase 1：Candidate Store

- schema migration。
- state machine、lease、dedupe、retry。
- structured event ingestion。

### Phase 2：Extraction（dry-run）

- deterministic extraction。
- LLM schema extraction。
- source/sensitivity/durability validation。
- 不寫入 memory files。

### Phase 3：Consolidation（shadow）

- 讀取最小相關記憶。
- 產生 mutation plan。
- duplicate/conflict/capacity policy。
- 只產出 proposed diff。

### Phase 4：Typed Repository 與 Apply

- lock/hash/atomic write。
- PEOPLE/MEMORY wrapper integrity。
- outbox/index sync/recovery。
- 小範圍 feature flag rollout。

### Phase 5：Subagent-assisted extraction（可選，獨立 PR）

- read-only worker。
- 最小 context。
- schema validation。
- 不改 mutation authority。

## 22. 測試計畫

至少包含：

1. 同一來源重跑不重複建立 candidate。
2. 不同說法的相同事實能語意去重。
3. owner 明確更正高於舊資料。
4. 模型推論不直接進長期記憶。
5. 新人物候選進 PEOPLE，不進 MEMORY。
6. owner 身分變更轉人工審核。
7. 短期事件只進 daily。
8. 30 天門檻與明確長期要求的例外。
9. 高敏感 payload 被拒絕／redact。
10. tombstone 防止被舊 session 復活。
11. lease expiry 可恢復。
12. 兩個 consolidation job 不會同時套用。
13. before hash 改變時舊 plan 被拒絕。
14. atomic write crash recovery。
15. substring replace 非唯一時拒絕。
16. PEOPLE wrapper 不會被破壞。
17. MEMORY 接近容量時先 prune/consolidate。
18. file write 成功、index update 失敗可 repair。
19. applied job 重播仍 idempotent。
20. tool 失敗不會被記成已完成。
21. current session 尚未 archive 時可處理 live envelope。
22. Subagent timeout/遲到結果不被套用。
23. audit/log 不含測試 secret。
24. shadow mode 完全不修改實體記憶。

自動化測試檔依既有規範：可在本機執行，但未經姊姊明確同意不得 commit、push 或納入 PR。

## 23. 驗收標準

- [ ] extraction 與 consolidation 是不同 job、不同責任。
- [ ] candidates 有來源、去重、信心、敏感度與狀態。
- [ ] candidate store 支援 lease、retry、idempotency。
- [ ] OWNER 不會被自動修改。
- [ ] PEOPLE/MEMORY/daily destination policy 已實作。
- [ ] LLM 只產生候選／operation，不自由覆寫整檔。
- [ ] apply 使用 hash check、lock 與 atomic write。
- [ ] file/FTS/vector drift 可偵測與修復。
- [ ] 敏感資料不進一般 log、embedding 或 worker context。
- [ ] tombstone 可阻止明確刪除的記憶復活。
- [ ] shadow mode 驗證完成後才開自動 apply。
- [ ] Subagent 不取得 mutation tools。
- [ ] `material/DESIGN.md` 已同步。
- [ ] build、migration、unit/integration tests 通過。

---

## 24. 回滾策略

- `memoryPipeline.enabled` 可立即關閉新 job。
- extraction、consolidation、apply 各自 feature flag。
- mutation audit 保存 before/after hash 與 operation，必要時產生反向 plan。
- 不自動刪除 session 原始證據。
- index 可從檔案重新建置。
- rollback 不應再次經過 LLM 自由生成。

---

## 25. 最終決策

這條管線的價值不是「讓 Furet 記更多」，而是讓記憶變得：

```text
先抽取候選
→ 再去重與判斷
→ 小範圍、可驗證地套用
→ 全程可追溯、可重試、可回滾
```

Subagent 可以協助理解，Bash policy 可以保護執行，但兩者都不能取代記憶 repository 自己的權限、資料完整性與隱私邊界。
